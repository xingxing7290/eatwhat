# 菜品回收站与兼容性

新版 Web 的菜品移除操作会将记录移入回收站，而不是物理删除。归档记录从普通菜谱、分类、标签、统计、新生成周计划和新加载的访客菜单中隐藏；原有排餐、回忆、图片文件和记录编号保留，回收站可搜索、分页和恢复。回收站不会自动清理或永久删除文件。

Web 仅在服务器明确提供归档能力及有效版本时开放操作。归档和恢复都携带原版本，服务器按家庭、记录、归档状态、修订标记和更新时间进行条件更新；冲突或响应不确定时需读取最新状态并由用户核对。未完成的核对提示保存在当前页面，离开时会提醒，但不是持久操作日志。缺少归档能力的旧服务器不会被当作可安全归档的服务器。

归档不等同于访问控制：历史排餐、回忆和按编号读取仍可看到归档菜品。新版服务在访客新建或修改订单时检查菜品是否可用；如果旧菜单中有已归档或不属于该家庭的菜品，会拒绝整次提交并让访客核对，不修改已保存订单。菜品检查和订单写入并非同一个数据库事务，因此两者之间并发归档仍存在竞态；已提交订单中的菜品快照保留。已打开的旧排餐页面或已生成的周计划草稿仍可能引用原编号，接口兼容旧客户端，不能保证旧客户端不会重新安排归档菜品。原有的 `DELETE /meals/:id` 物理删除接口保留给旧客户端，仍可能造成历史引用缺失；新版 Web 的回收站不调用该接口。直接数据库写入或同时运行未升级的旧服务也不受条件版本保护。

访客页面遇到订单版本冲突时保留当前草稿，需要明确确认后才用最新订单替换。网络失败、服务端错误或不完整的提交响应会提示结果未确认，并要求先联系主人核对；警告尽力保存在当前浏览器标签页的会话存储中，但草稿本身不会在刷新后保留。如果浏览器拒绝保存订单凭证，页面会提示关闭或刷新后可能无法继续修改。订单提交尚无服务端幂等键，确认后重试仍可能与迟到的请求重复，不能将此提示视为防重保证。

历史记录缺少归档字段时视为未归档，不需要批量迁移。部署前应保留私有数据库和上传文件备份，并在隔离环境验证归档、恢复、历史排餐和访客菜单；不要自动修改即将到期的旧服务器。
