# 想吃清单投票与兼容性

新版 Web 仅在服务端返回 `supportsSetVote` 和当前用户投票状态时开放投票，使用 `PUT /wishlist/:id/vote` 和布尔值明确设置或取消自己的票。服务端对当前家庭记录使用原子 `$addToSet` / `$pull`，同一目标状态的重复请求不会增加重复票，不同成员的投票也不会通过整数组覆盖彼此。列表中的菜品、创建者和投票成员只填充当前家庭范围内的引用。

旧客户端的 `POST /wishlist/:id/vote` 仍保留切换语义，改为原子数组操作以避免不同成员覆盖彼此；该切换接口本身不是幂等的，重复提交仍可能再次切换。旧服务器未声明新能力时，新版 Web 暂不开放投票，避免将旧切换接口当作幂等操作使用。

新版 Web 修改状态或删除时要求服务器明确提供 `supportsConditionalActions` 和有效版本。请求以家庭、记录、修订标记及更新时间进行条件匹配；其他应用层写入（包括投票和关联菜谱）会更新修订标记，过期操作返回冲突并要求刷新核对。从想吃清单安排排餐时，Web 会先读取并检查关联和版本，仅对仍为“想吃”的记录尝试条件更新为“已安排”；如果状态已完成或版本冲突，排餐仍可保存，但不会覆盖新的清单状态。

旧数据没有修订标记或更新时间时使用 `null` 匹配缺失值，无需批量迁移。旧客户端不带版本的状态修改和删除仍保留兼容，因此自身的无条件操作可能覆盖或删除较新的内容；直接数据库写入、绕过模型钩子的批量操作，以及同时运行未升级的旧服务器实例也不受修订标记保护。一次刷新不能保证先前不确定的网络请求不会随后完成，临时核对提示保存在当前页面，不是持久的操作日志。部署前应备份并在隔离环境验证新旧客户端及家庭数据；不要自动改动即将到期的旧服务器。
