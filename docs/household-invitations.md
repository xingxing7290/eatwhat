# Household invitations and recovery

Invitation codes identify one household and should be shared only with trusted people. Newly generated or refreshed codes contain 20 hexadecimal characters generated from cryptographic randomness. Existing shorter codes remain valid until their household explicitly refreshes them. Refreshing invalidates the previous code for subsequent requests; it does not remove current members. Invitation links use a URL fragment, which is not sent as part of the HTTP request, and the web app removes the code from the address after reading it.

The `User.householdId` field is authoritative for a user's current household. The household's `members` array is a denormalized compatibility cache and may lag after interruptions or concurrent requests. User-facing member lists are built from current user records rather than that cache. The server compares the observed membership before a switch, and the web app asks for confirmation and verifies the returned account and household before showing success.

The current standalone MongoDB deployment does not make the user update, compatibility-cache updates, and household provisioning a single transaction. A failure after a write can leave a membership cache stale, or, during a concurrent account-provisioning conflict, leave a newly created household without an assigned account. The application reports uncertain outcomes rather than automatically retrying a switch. Do not automatically delete households or merge records to repair these situations: first preserve a verified private backup, inspect current `User.householdId` values and the affected households, and resolve deliberately. Protect database access and review existing short codes before deciding whether to rotate them.

Deploy compatible server and web versions together. Test registration with two different households, an old and a refreshed invitation, cancellation of a switch, and a successful switch before retiring an existing server. Invitation codes are credentials, not a substitute for authentication or request-rate controls; do not publish them or put them in logs.

## Household name editing

The web settings page requires the server's conditional name version before saving. A concurrent name change is rejected rather than overwritten; the page retains the entered name and unsaved profile fields, then lets the user inspect the latest name and either adopt it or keep the draft for a separate, explicit save. A lost or malformed response is treated as uncertain and must be reviewed before retrying. A previously sent request may still complete after a review, so the displayed latest value is not a transactionally frozen snapshot.

Saving a profile, uploading an avatar or refreshing the invitation must not silently advance the version associated with an unsaved household-name draft. If no name draft is present, those responses may refresh the displayed name and version normally.

The server atomically compares a name-specific revision and changes it on each supported name update. Missing revisions in legacy documents are supported; existing clients without a version remain compatible but can still overwrite a concurrent name and therefore do not get the same protection. Document `save()` name edits made with the upgraded model also rotate the revision; direct database writes, old server instances and older maintenance code may not. Invitation rotations and membership-cache changes do not change the name revision. Deploy compatible server and web versions together and validate with two household members before relying on this protection.
