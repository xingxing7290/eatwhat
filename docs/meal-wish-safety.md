# 安全点菜：迁移与验证

新接口 `POST /api/wishlist/meal` 依赖 MongoDB 的 `uniq_open_household_meal` 唯一部分索引。索引按家庭和菜品约束 `status: open` 的记录；未关联菜品的想吃记录以及已安排、已完成的历史记录不受该约束。重复请求会返回已有记录，不会覆盖其创建人、投票或备注。家庭访问仍由服务端验证。

服务端不会在启动时自动创建该索引或删除重复记录。新接口只有在检查到预期索引时才会接受写入；缺少索引时返回 `MEAL_WISH_INDEX_REQUIRED`。旧版客户端仍可调用原接口，但启用索引后，重复写入、关联或把已有记录改回“想吃”可能返回 `WISH_ALREADY_OPEN` 冲突；上线前需要检查旧客户端的错误处理。

## 迁移前

1. 在新服务器或隔离环境中先恢复并验证数据库备份，确认应用和数据库版本；不要在资源紧张的旧生产服务器上直接演练。
2. 用受保护的环境变量向脚本提供 `MONGO_URI`，并明确指定预期数据库名。不要把连接字符串、账号密码写入仓库或命令行历史。
3. 在 `server` 目录运行只读检查：`node scripts/meal-wish-index.js --database whateat`。输出仅包含数据库名、是否已有安全索引、重复组数量及无效菜品或家庭引用数量。
4. 如果存在重复组或无效引用，停止迁移；由数据负责人备份并逐项核对、处理。脚本不会自动修改、合并或删除任何清单记录。检查与创建之间仍可能有新写入，因此数据库创建唯一索引时也会再次验证；如有冲突会失败。
5. 确认备份和维护窗口后，才在目标数据库运行 `node scripts/meal-wish-index.js --database whateat --apply`。脚本会再次检查数据库名和重复组，创建索引后复核定义。索引可能增加数据库负载，应先在相同规模的隔离环境验证。
6. 部署新后端和 Web 端，确认 `GET /api/wishlist?status=open&includeCapabilities=true` 返回 `supportsAtomicMealWish: true`，并测试同家庭并发添加、不同家庭隔离、已完成后再次添加、旧客户端冲突提示及列表恢复。

如需回滚代码，先评估已创建索引对旧客户端写入行为的影响，保留备份并安排维护窗口；不要自动删除索引或清理历史记录。

隔离 MongoDB 的并发集成用例见 [测试说明](../server/test/README.md)。只有真实数据库集成验证通过后，才能把跨设备防重视为已验证；浏览器模拟和单元测试不能代替它。

Web 想吃清单的搜索、状态和优先级筛选仅作用于当前已读取的清单，不会更改记录或替代服务端权限检查。状态无法识别的记录会放在“状态待核对”中并暂时禁止操作；缺少必要标识或出现重复标识时，页面会提示读取结果不完整，而不是静默遗漏记录。如果筛选隐藏了本页创建或关联结果待核对的记录，页面会提示清除筛选。当前列表接口仍返回家庭的全部记录，筛选并不是服务端分页。
