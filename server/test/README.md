# Isolated MongoDB integration check

## Local meal-wish concurrency check

With a trusted local MongoDB 7 `mongod` executable and Node.js, set `EATWHAT_TEST_MONGOD` to its absolute path and run `node test/mealWishMongo.local.integration.cjs` from the server directory. Set the system temporary directory to a disk with free space first: each run can retain roughly 300 MB. The test starts its own process with a fresh temporary data directory, an ephemeral port and `127.0.0.1` binding; it verifies the process-reported directory, port, bind address and empty database before writing synthetic fixtures. It rejects an externally supplied database URI, stops its own MongoDB process on completion and prints the retained synthetic test directory for inspection and later manual cleanup. It does not connect to or clean up an existing database.

The local check exercises real indexes and HTTP endpoints using 16 parallel requests from two users in one household, separate households, invitation rotation and competing household switches, partner-only dashboard reminders and priority ordering, migration-audit rejection, legacy conflicts, re-adding a completed meal, and versioned shopping-list concurrency and index audit. See `docs/shopping-list-safety.md` for shopping-list rollout precautions. The broader Docker-based integration below remains a separate check.

To additionally exercise the built dashboard, recipe page, scheduling, weekly draft editing, shopping list and invitation flow in desktop and mobile Chromium against these real endpoints and the temporary database, build `client/dist`, ensure the client Playwright dependency and Chromium are installed, and set `EATWHAT_TEST_BROWSER=1` (optionally `CHROME_PATH` for an existing browser). The test verifies partner reminders, real category and search queries, draft-only changes, household registration and switching, concurrent updates and conflict recovery, starts a loopback-only static/proxy server, uses test-only accounts and data, and saves a mobile screenshot in the retained temporary directory.

## Docker-based application integration

Run `sh test/run-isolated-mongo.sh` from the server directory on a Linux host with Docker, `timeout`, MongoDB 7 and a locally available backend image containing dependencies at `/app/node_modules`. The default images are `mongo:7.0` and `eatwhat-backend-local:latest`; set `EATWHAT_TEST_MONGO_IMAGE` or `EATWHAT_TEST_BACKEND_IMAGE` to override them.

The script creates a temporary internal Docker network, a fresh MongoDB container without host ports or persistent volumes, and a separate backend test container with the current server source mounted read-only. The test copies only the required source into the disposable container and writes test uploads there. It removes the containers and network on exit. No production database or credentials are used. The test refuses any MongoDB URI except the dedicated test address.

The test exercises real MongoDB indexes, HTTP login and JWT middleware, month-end schedule reads, conditional update and concurrent insert conflicts, reporting partially applied days, retrying against a fresh snapshot, stale single-day selection, safe wish-to-meal linking, 12 concurrent atomic meal-wish requests and legacy conflicts, repeating a dish across anniversary meal slots, household data isolation, concurrent recipe edits and upload cleanup. All accounts, passwords and the JWT secret are test-only. It does not exercise the deployed production service. See `docs/meal-wish-safety.md` for index migration and rollout precautions.

## Browser-to-database full-stack check

This separate test runs the built web client, the current server source, and a fresh MongoDB together, then drives the real interface with Playwright. Build `client/dist` from the version being tested first (`cd client && npm ci && npm run build`). On a Linux Docker host containing that build, the server source and `client/nginx.conf`, run `sh server/test/start-isolated-stack.sh` from the repository root. The script uses the same MongoDB and backend image defaults and overrides as above, plus `EATWHAT_TEST_NGINX_IMAGE` (default `nginx:alpine`). It prints the frontend container's private IP.

There are no published container ports: on a machine that can reach the Docker host over SSH, forward its loopback port 5189 to the printed private IP, for example `ssh -N -L 127.0.0.1:5189:<frontend-private-ip>:80 <docker-host>`. From `client`, run `EATWHAT_E2E_URL=http://127.0.0.1:5189 npm run test:full-stack`; optionally set `CHROME_PATH` to a compatible local Chromium executable. The client dependencies include Playwright; otherwise install its Chromium browser before running. The test refuses any other URL and checks an isolated-stack response marker before writing data.

The browser check covers login, profile and avatar updates, recipe creation and scheduling, memory photo upload and album, weekly plan application, shopping list, wishlist, invitation-link registration and isolation between two households. Its accounts, JWT secret, uploads and MongoDB are disposable and test-only. The startup script cleans up on failure; after a successful run stop the tunnel and run `sh server/test/stop-isolated-stack.sh` on the Docker host. The stop script checks the test labels before removing its specifically named containers and network. Do not point this test at production.

The full-stack upload checks verify that avatar and recipe-image URLs retain a non-standard public port through the frontend proxy. When an upstream proxy terminates TLS or otherwise hides the public origin, configure `PUBLIC_BASE_URL` with the externally reachable base URL; do not assume an internal proxy's scheme or port represents the public address. Existing stored URLs are not rewritten by the server change.
